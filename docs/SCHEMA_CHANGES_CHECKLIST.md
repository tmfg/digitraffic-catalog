# Schema Changes Checklist

This document outlines all the components that must be updated when making schema changes, particularly cardinality modifications to dataset properties.

## ⚠️ Important: Database Migration Guarantee

**All database migrations are GUARANTEED to complete successfully before the application starts.**

This principle applies to any migration (cardinality changes, data transformations, schema updates, etc.):

- Migrations run as part of container initialization (Alembic upgrade)
- All data transformations must complete before the app executes any code
- Application code should **only handle the new format**
- **No backward compatibility needed** in application layers (data converter, RDF export, etc.)

**Design principle:** Assume the migration has already succeeded. Don't implement fallback logic for old formats.

## Overview

The catalog uses a **multi-layer architecture** where schema changes must propagate through several independent systems:

```
RDF/DCAT-AP Specification
         ↓
Schema Generator (dcat_schema_transpiler)
         ↓
YAML Schema (mobility_dcat.yaml)
         ↓
UI Forms & Validation
         ↓
Python Data Models
         ↓
Data Conversion & Serialization
         ↓
Search Indexing
         ↓
Database Storage
         ↓
RDF Export
```

**Critical rule:** Changes are **not complete** until ALL layers are updated and tested together.

## Checklist: Cardinality Changes

Use this checklist when you change a property's cardinality (e.g., from 0..1 to 0..n, or single to repeating).

### 1. Schema Generator (`dcat_schema_transpiler`)

**Location:** `dcat_schema_transpiler/dcat_schema_transpiler/ckan_schema/mobility_dcat_ap_converter/classes/`

**Files to modify:** Converter class for the affected property (e.g., `quality_annotation.py`, `assessment.py`)

⚠️ **Important:** When adding new field types or changing presets, always include `form_snippet` to specify the form input widget. See [SCHEMA_CONFIGURATION.md](./SCHEMA_CONFIGURATION.md) for details on preset vs form_snippet and available templates.

**Changes required:**

- [ ] **For `0..1 → 0..n` (single to repeating):**
  - Modify `get_schema()` method
  - Add `form_blanks: 0` parameter
  - Wrap field in `repeating_subfields` list
  - Move validation/metadata to subfield level
  - Extract `label` and `help_text` individually if needed
  - Move `preset` to subfield definition
  - Add `form_snippet` to match the preset (see [SCHEMA_CONFIGURATION.md](./SCHEMA_CONFIGURATION.md) for available snippets)
  
  Example:
  ```python
  return {
      "field_name": "my_field",
      "form_blanks": 0,
      **super().get_necessity_mapping(clazz_p.iri),
      "repeating_subfields": [
          {
              "field_name": "my_subfield",
              "label": {...},
              "preset": "url",
              "form_snippet": "url_input.html",  # Add form_snippet to match preset
          }
      ],
  }
  ```

- [ ] **For `0..n → 0..1` (repeating to single):**
  - If using `AggregateRangeValueConverter`: modify `get_aggregate_schema()`
  - Return the accumulated `self.__aggregate_schemas` list
  - `ClassConverter._append_schema()` recognizes lists and appends each field separately
  - Results in flat fields at top level, not wrapped in repeating_subfields
  - Remove `repeating_subfields` logic
  
  Example:
  ```python
  def get_aggregate_schema(self) -> List[Dict]:
      # Property changed from repeating (0..n) to single (0..1)
      # Return accumulated individual field schemas
      # ClassConverter will flatten these as separate fields
      return self.__aggregate_schemas
  ```
  
  **Important:** Returning `None` breaks the ClassConverter dispatch logic (inserts `None` into fields array). Always return the accumulated schemas list.

- [ ] **Verify:** Run Python syntax check
  ```bash
  python3 -m py_compile <file>
  ```

**Why:** Schema generators are called during regeneration workflow (`README.md:182-204`). Without updates, regeneration will undo manual YAML fixes.

### 4. Data Converter (`mobility_data.py`)

**Location:** `ext/ckanext-digitraffic_core/ckanext/digitraffic_core/model/mobility_data.py`

**Changes required:**

- [ ] **For `0..1 → 0..n` (single to repeating):**
  - Find converter method (e.g., `_quality_annotation`)
  - Change from accessing single value to iterating over list
  - Build list of objects with subfield values
  
  Example:
  ```python
  # Before
  if "quality_description" in dataset_dict:
      dataset["quality_annotation"] = dataset_dict["quality_description"]
  
  # After
  if "quality_description" in dataset_dict:
      quality_list = dataset_dict["quality_description"]
      dataset["quality_annotations"] = [
          {"quality_url": item.get("quality_url")}
          for item in quality_list if item.get("quality_url")
      ]
  ```

- [ ] **For `0..n → 0..1` (repeating to single):**
  - Change from iterating over list to accessing single dict
  - Extract individual field values from single dict
  
  Example:
  ```python
  # Before
  if "assessment" in dataset_dict:
      assessments = dataset_dict["assessment"]
      dataset["assessments"] = [
          {"date": a.get("assessment_date"), ...}
          for a in assessments
      ]
  
  # After
  if "assessment_date" in dataset_dict or "assessment_result" in dataset_dict:
      dataset["assessment"] = {
          "date": dataset_dict.get("assessment_date"),
          "result": dataset_dict.get("assessment_result"),
      }
  ```

- [ ] **Update method signature if needed:** Parameter names should match new structure
- [ ] **Add error handling:** Handle missing/null values gracefully
- [ ] **Verify:** Test converter with sample data

**⚠️ Special Note: Vocabulary Properties**

For properties using `SchemaChoiceVocabulary` or `SchemaVocabulary` subclasses
(e.g., `GeoreferencingMethod`, `TransportMode`, `Frequency`):

The vocabulary class constructor expects a **single IRI string**, not a list. For repeating
properties, **iterate and create one object per IRI** using a list comprehension:

✅ **CORRECT**:
```python
"georeferencing_method": [
    GeoreferencingMethod(entry)
    for entry in dataset_dict["georeferencing_method"]
]
```

❌ **INCORRECT** (causes `TypeError: unhashable type: 'list'`):
```python
"georeferencing_method": GeoreferencingMethod(dataset_dict["georeferencing_method"])
```

See reference implementations:
- `transport_mode`: [mobility_data.py:405-410](/ext/ckanext-digitraffic_core/ckanext/digitraffic_core/model/mobility_data.py#L405)
- `spatial`: [mobility_data.py:413](/ext/ckanext-digitraffic_core/ckanext/digitraffic_core/model/mobility_data.py#L413)

**Why:** This converts CKAN form submission (key-value pairs) into runtime data model objects.

### 8. Database Migration

**Location:** `ext/ckanext-digitraffic_core/ckanext/digitraffic_core/migration/digitraffic_core/versions/`

**Changes required:**

- [ ] **Create new migration file with the CKAN CLI** (don't create it by hand):
  ```bash
  ckan generate migration -p digitraffic_core -m 'short description'
  ```
  - Generates `versions/<revision-id>_<slug>.py` with `revision`/`down_revision` filled in
  - Use CKAN 2.12+ Alembic migration approach: https://docs.ckan.org/en/2.12/contributing/database-migrations.html
  - See [DATABASE_MIGRATIONS.md](./DATABASE_MIGRATIONS.md) for the full migration guide

- [ ] **⚠️ DDL vs. data changes:**
  - **Never do DDL on CKAN tables** (`package`, `package_extra`, `resource`, ...): no added/altered/dropped columns, indexes, constraints or foreign keys
  - **Data changes in CKAN tables are allowed** (`UPDATE` etc.): this is how existing datasets are converted when a stored format changes (the rest of this layer)
  - Use Alembic's `op.*` DDL operations only for the extension's own tables

- [ ] **CKAN 2.12+ Database Structure:**
  > CKAN 2.12 migrated from `package_extra` table to JSONB `extras` column on `package` table
  - Extras are now stored as flat JSON: `package.extras = {"key": "value", ...}`
  - Use PostgreSQL JSONB operators: `->`, `->>`, `jsonb_build_object()`, etc.
  - See: https://github.com/ckan/ckan/blob/master/ckan/migration/versions/106_12d64978ab44_faster_extras.py

- [ ] **⚠️ CRITICAL: Scheming stores repeating fields as JSON-encoded STRINGS:**
  > **Repeating fields (0..n cardinality) are stored as JSON-encoded strings, not native JSONB arrays.**
  > When accessing them in SQL, you MUST extract as text (`->>`) and cast to JSONB (`::jsonb`).
  > **This is the most common migration bug.**

  Example data:
  ```json
  // ✓ Repeating field (0..n) - stored as TEXT string
  package.extras = {
    "assessment": "[{\"date\": \"2026-01-01\", \"result\": \"pass\"}]"
    // ^ This is a string, not a JSONB array!
  }

  // ✓ Flat field (0..1) - stored as native JSONB
  package.extras = {
    "assessment_date": "2026-01-01"  // Native JSONB value
  }
  ```

  **Wrong SQL (will fail):**
  ```sql
  -- ✗ Treats string like array - causes error
  jsonb_array_length(extras->'assessment')
  extras->'assessment'->0->>'date'
  ```

  **Correct SQL:**
  ```sql
  -- ✓ Extract text, cast to JSONB, then access
  jsonb_array_length(((extras->>'assessment')::jsonb))
  (((extras->>'assessment')::jsonb)->0->>'date')

  -- Breakdown:
  -- extras->>'assessment'    = Extract as text
  -- ::jsonb                  = Cast text to JSONB array
  -- ->0                      = Access first element
  -- ->>'date'                = Extract text field
  ```

  **Python equivalent (for reference):**
  ```python
  # This is why Python code uses json.loads():
  assessments = json.loads(package.extras.get("assessment") or "[]")
  # SQL must do the same with ::jsonb cast
  ```

- [ ] **For `0..1 → 0..n` (single to repeating):**
  - Transform flat extras → list structure via UPDATE SQL query
  - Use JSONB operators to build arrays, e.g., `jsonb_build_array(jsonb_build_object(...))`
  - Handle NULL/missing values (don't include in transformed data)
  - Preserve data integrity (no data loss)

  Example (SQL-based):
  ```python
  def upgrade():
      bind = op.get_bind()
      query = text("""
          UPDATE package
          SET extras = extras || jsonb_build_object(
              'quality_description_list',
              jsonb_build_array(
                  jsonb_build_object('quality_url', extras->>'quality_description')
              )
          ) - 'quality_description'
          WHERE extras->>'quality_description' IS NOT NULL
      """)
      bind.execute(query)
  ```

- [ ] **For `0..n → 0..1` (repeating to single):**
  - Transform array structure → flat extras via UPDATE SQL query
  - Extract first element if multiple exist (log warning)
  - **REMEMBER: Repeating fields are JSON-encoded STRINGS - use `::jsonb` cast!**
  - Use JSONB operators: `(((extras->>'array')::jsonb)->0->>'key')` for first element access
  - Handle missing/NULL values (delete from JSON with `-` operator)

  Example (SQL-based, CORRECT with cast):
  ```python
  def upgrade():
      bind = op.get_bind()
      query = text("""
          UPDATE package
          SET extras = (
              (extras - 'assessment') || jsonb_build_object(
                  'assessment_date', (((extras->>'assessment')::jsonb)->0->>'assessment_date'),
                  'assessment_result', (((extras->>'assessment')::jsonb)->0->>'assessment_result')
              )
          )
          WHERE extras->>'assessment' IS NOT NULL
          AND jsonb_array_length(((extras->>'assessment')::jsonb)) > 0
      """)
      bind.execute(query)
  ```

  **Note the differences from the wrong example:**
  - ❌ Wrong: `extras->'assessment'->0` (treats string as JSONB array)
  - ✅ Correct: `((extras->>'assessment')::jsonb)->0` (extracts text, casts to JSONB, then accesses)

- [ ] **Write downgrade function:** Reverse transformation (SQL-based)

  ⚠️ **CRITICAL FOR REPEATING FIELDS:** When downgrading from 0..1 → 0..n, cast the constructed array to TEXT to restore the original Scheming storage format. Without this cast, the old schema will receive native JSONB arrays instead of the expected JSON-encoded strings, breaking the data converter (which calls `json.loads()` on the value).

  Example (WRONG - will break old converter):
  ```python
  # ✗ WRONG - stores native JSONB array
  jsonb_build_object(
      'assessment',
      jsonb_build_array(jsonb_build_object(...))  # Still JSONB array
  )
  ```

  Example (CORRECT - restores original format):
  ```python
  # ✓ CORRECT - casts array to text string (Scheming format)
  def downgrade():
      bind = op.get_bind()
      query = text("""
          UPDATE package
          SET extras = (
              (extras - 'assessment_date' - 'assessment_result') || jsonb_build_object(
                  'assessment',
                  jsonb_build_array(
                      jsonb_build_object(
                          'assessment_date', extras->>'assessment_date',
                          'assessment_result', extras->>'assessment_result'
                      )
                  )::text  -- ← CAST TO TEXT - this is critical!
              )
          )
          WHERE extras->>'assessment_date' IS NOT NULL
             OR extras->>'assessment_result' IS NOT NULL
      """)
      bind.execute(query)
  ```

  **Why:** Scheming stores repeating fields as JSON-encoded STRINGS in JSONB. After rollback, the old Scheming schema will try to `json.loads()` the value. If it receives a native JSONB array instead, the conversion fails.

- [ ] **Add logging:** Log transformation counts and any warnings
- [ ] **Search index (local environments only):** raw SQL updates don't update Solr, so the API keeps returning the old structure until reindexed. Don't call `ckan.lib.search.rebuild()` from the migration: the CKAN app isn't loaded in the Alembic context. See [SOLR_CACHE.md](./SOLR_CACHE.md)

- [ ] **Verify:** Test migration on staging database before prod deployment

**Why:** Database stores dataset metadata as JSONB in `package.extras` column. Must transform existing data format before application code accesses new structure.

## 🔍 Critical Principle: Model Consistency Across All Layers

**When ANY property structure changes, the data model representation must be updated in ALL layers simultaneously.**

This principle applies to:
- Cardinality changes (0..1 ↔ 0..n)
- Storage structure changes (nested object ↔ flat scalar fields)
- Field composition changes (single field ↔ multiple related fields)

### Why This Matters

The catalog architecture has multiple independent models for the same data:

| Layer | Model | Location |
|-------|-------|----------|
| **Schema Definition** | YAML field structure | `mobility_dcat.yaml` (auto-generated from converter) |
| **Python Runtime** | Type annotations, Python class | `model/dataset.py` |
| **Display HTML** | HTML structure (nested divs, tables, lists) | `templates/additional_info.html`, etc. |
| **Page Object Readback** | Locator patterns, text parsing logic | `e2e/page-object-models/dataset-page.ts` |
| **Database** | JSONB structure, column layout | `package.extras` JSON or separate columns |
| **RDF Output** | Triple patterns, cardinality | `model/dataset.py` RDF serialization |

**If these models don't match, tests will pass in one layer and fail silently in another.**

### Real Example: Assessment Property

Assessment changed from **repeating nested objects** (0..n) to **single object from flat fields** (0..1):

**Before (nested object model):**

## Common Pitfalls

### ❌ Forgetting to update Schema Generator
**Problem:** Next regeneration overwrites YAML fixes
**Solution:** Always update converter when changing cardinality
**Check:** Verify regenerated YAML matches expected structure

### ❌ Mismatched Field Names
**Problem:** `quality_description` in YAML but `quality_annotations` in Python model
**Solution:** Keep names consistent across all layers, or add explicit mapping
**Check:** Compare layer-by-layer during review

### ❌ Missing Search Configuration
**Problem:** Repeating field not indexed correctly, search fails
**Solution:** Add field to `DATASET_FIELDS_WITH_REPEATING_SUBFIELDS` for repeating
**Check:** Test search after deployment

### ❌ Incomplete Database Migration
**Problem:** Existing data not transformed, old code paths still used
**Solution:** Always write both upgrade and downgrade functions
**Check:** Test migration with real data before deploying

### ❌ Breaking RDF Export
**Problem:** Generated RDF doesn't match spec (single vs multiple properties)
**Solution:** Verify list comprehension (repeating) vs conditional (single) in `to_rdf_triples()`
**Check:** Validate RDF output against ontology

### ❌ No Validator Updates
**Problem:** Form accepts invalid data, validation doesn't work
**Solution:** Check if field has custom validators, update if cardinality changes affect logic
**Check:** Test form with boundary cases (empty, null, multiple values)

## Deep Dive: AggregateRangeValueConverter Dispatch Logic

When a converter inherits from `AggregateRangeValueConverter`, the schema generation follows a specific pattern. Understanding this is critical for implementing `get_aggregate_schema()` correctly.

### How ClassConverter Dispatches Aggregate Converters

```python
# ClassConverter.convert() excerpt:
elif isinstance(converter, AggregateRangeValueConverter):
    for p in included_properties:
        schema = self._get_property_schema(p, converter, omit, is_required)
        self._append_aggregate(schema, converter)      # Accumulates in __aggregate_schemas
    
    property_schemas = converter.get_aggregate_schema()
    self._append_schema(property_schemas)               # Appends to __schema_fields
```

### The Pattern: Accumulate, Then Return

**Step 1: Accumulation**
- For each property (e.g., `assessment_date`, `assessment_result`):
  - `converter.get_schema()` generates field definition
  - `converter.add_to_aggregate()` accumulates it in `self.__aggregate_schemas`

**Step 2: Return**
- After all properties accumulated:
  - `converter.get_aggregate_schema()` is called
  - Returns the accumulated schemas
  - `_append_schema()` processes the return value

### Why Return None Fails

If `get_aggregate_schema()` returns `None`:

```python
# _append_schema(None):
def _append_schema(self, schema):
    if isinstance(schema, list):
        for field in schema:
            self.__schema_fields.append(field)
    else:
        self.__schema_fields.append(schema)  # ← Appends None!

# Later, post_process_schema() tries:
for field in self.__schema_fields:
    field.get("field_name")  # ← ERROR: 'NoneType' has no attribute 'get'
```

### The Correct Return Value

Always return what was accumulated: `self.__aggregate_schemas`

```python
def get_aggregate_schema(self) -> List[Dict]:
    # Converter accumulated assessment_date and assessment_result
    return self.__aggregate_schemas  # Returns [field1_dict, field2_dict]
    
# _append_schema([field1_dict, field2_dict]):
def _append_schema(self, schema):
    if isinstance(schema, list):  # ← Recognized as list
        for field in schema:
            self.__schema_fields.append(field)  # ← Each field appended separately
```

### Result in YAML

Flat fields at top level (not repeating):
```yaml
assessment_date:
  field_name: assessment_date
  preset: date
assessment_result:
  field_name: assessment_result
  preset: url
```

### When to Use Which Pattern

| Scenario | Converter | get_aggregate_schema() | Result |
|----------|-----------|------------------------|--------|
| Repeating section (0..n) | AggregateRangeValueConverter | Dict with repeating_subfields | Wraps fields in repeating section |
| Flat fields (0..1) | AggregateRangeValueConverter | List[Dict] from __aggregate_schemas | Appends each field separately |
| Single field | Non-aggregate converter | Single Dict | Appends one field |

## Regenerating the Schema

After updating the Schema Generator files (Step 1), you must regenerate `mobility_dcat.yaml` to reflect your changes.

### Prerequisites

- Poetry installed
- Changes committed to the transpiler (Step 1 items above)

### Step-by-Step Guide

#### 1. Install Transpiler Dependencies

```bash
cd dcat_schema_transpiler
poetry install
```

This installs Python dependencies like `rdflib`, `pyyaml`, and `httpx`.

#### 2. Run the Transpiler

```bash
poetry run python dcat_schema_transpiler/transpiler.py
```

**What it does:**
- Reads RDF definitions from `mobility_dcat_ap/dataset.py`
- Calls all schema converter classes (e.g., your updated `assessment.py`)
- Generates a new schema file at `dcat_schema_transpiler/output/schema.yaml`

**Output:**
```
Creating file <repo>/dcat_schema_transpiler/output/schema.yaml
```

#### 3. Verify Generated Schema

```bash
# View the generated schema (optional)
cat output/schema.yaml | head -100

# Verify your changes are present (example for assessment fields)
grep -A 3 "assessment_date\|assessment_result" output/schema.yaml
```

Expected output for assessment fields:
```yaml
- field_name: assessment_date
  preset: date
  form_snippet: date.html  # ← Verify this was added
  ...
- field_name: assessment_result
  preset: url
  form_snippet: url_input.html  # ← Verify this was added
  ...
```

#### 4. Copy to CKAN Extension

```bash
cp output/schema.yaml ../ext/ckanext-digitraffic_core/ckanext/digitraffic_core/schemas/mobility_dcat.yaml
```

**Important:** Always use `cp`, never manually edit the destination YAML file. It's auto-generated and manual edits will be lost on next regeneration.

#### 5. Reload CKAN

```bash
cd ../local-env
./dev.sh reload
```

This restarts the CKAN application with the new schema.

#### 6. Test the Changes

1. **Create a new dataset** in the CKAN web UI
2. **Navigate to relevant section** (e.g., Assessment for assessment fields)
3. **Verify UI changes:**
   - Form fields appear (not hidden)
   - Proper widgets are used (date picker for dates, URL input for URLs, etc.)
   - Field labels and help text are correct

### Troubleshooting

| Problem | Cause | Solution |
|---------|-------|----------|
| `poetry: command not found` | Poetry not installed | Install Poetry from https://python-poetry.org |
| `ModuleNotFoundError: rdflib` | Dependencies not installed | Run `poetry install` |
| `schema.yaml` not generated | Transpiler error | Check output for error messages; verify Python files have no syntax errors |
| Changes not appearing in UI | CKAN not reloaded | Run `./dev.sh reload` and clear browser cache (Ctrl+Shift+Delete) |
| Wrong field types showing | Old schema cached | Clear CKAN cache: `./dev.sh reload` or restart container |

### Common Mistakes

❌ **Don't do this:**
- Manually edit `mobility_dcat.yaml` directly (edits will be overwritten)
- Forget to run `poetry install` before running transpiler
- Skip the reload step (changes won't be visible in UI)
- Copy schema from wrong path

✅ **Do this:**
- Always modify the source (transpiler classes, not YAML)
- Run full workflow: modify → regenerate → copy → reload → test
- Verify changes in generated YAML before copying
- Test in CKAN UI after reloading
